SceneIt is a prototype web application that lets someone describe a moment in natural language—such as “a person walking through the rain”—and attempts to locate the matching timestamp inside an indexed YouTube video.

The current system combines:

Flask for the web server and JSON API
Twelve Labs for semantic video search across visual and audio content
YouTube IFrame API for browser playback
Tailwind CSS and custom CSS for the interface
A small local JSON mapping file connecting Twelve Labs video IDs to YouTube video IDs
A command-line script that downloads YouTube videos and submits them to Twelve Labs for indexing
A separate, experimental RunPod + Qwen vision model diagnostic that is not connected to the application
The core MVP is implemented and the homepage is currently running. However, the project is still at prototype maturity. It lacks automated tests, durable storage, production observability, indexing administration, concurrency protection, robust error handling, and a genuinely reproducible sharing system.

The most important architectural issue is that the documented/intended YouTube migration called for direct URL-based indexing without downloading videos, but the current indexing script still downloads the entire video using yt-dlp before uploading it to Twelve Labs.

2. Product concept
The intended user experience is:

An administrator indexes one or more YouTube videos.
Twelve Labs analyzes their visual and audio content.
A user opens SceneIt and describes a moment.
The backend submits the description to Twelve Labs.
Twelve Labs returns a matching video ID and time range.
SceneIt maps the Twelve Labs video ID back to the original YouTube video ID.
The browser embeds that YouTube video at the matching timestamp.
The selected segment automatically loops.
This is a focused “moment finder,” not currently a general video library, video editor, recommendation engine, or conversational assistant.

5. Current runtime architecture
Request flow
Browser
   |
   | GET /
   v
Flask renders templates/index.html
   |
   | User enters a description
   |
   | POST /search
   | { "query": "..." }
   v
Flask backend
   |
   | Twelve Labs semantic search
   v
Twelve Labs index
   |
   | Returns video_id, start, end, confidence/rank
   v
Flask reads video_mapping.json
   |
   | Maps Twelve Labs video ID to YouTube ID
   v
Browser receives result
   |
   | Creates YouTube iframe at returned timestamp
   v
YouTube playback with client-side looping
Backend initialization
At startup, main.py reads:

TWELVE_LABS_API_KEY
TWELVE_LABS_INDEX_ID
If an API key is present, it creates the Twelve Labs client.

A notable detail is that the client is created only once at module import time. If configuration changes while the server is running, the server must be restarted.

Search endpoint
The search endpoint expects:

{
  "query": "a natural language scene description"
}
It then calls Twelve Labs using the configured index and:

search_options=["visual", "audio"]
Only the first match is used.

A successful result resembles:

{
  "success": true,
  "start": 42.1,
  "end": 48.7,
  "confidence": 0.95,
  "query": "the requested description",
  "youtube_video_id": "..."
}
If no match is returned:

{
  "success": false,
  "message": "No matches found for your query."
}
Confidence handling
The application tries to normalize different Twelve Labs response formats:

Numeric confidence is used directly.
String values are converted:
high → 0.95
medium → 0.75
low → 0.5
Missing confidence is estimated from result rank.
The rank-derived confidence is synthetic. It is useful for presentation but should not be treated as a calibrated probability.

Because only the top result is used, the rank is usually likely to be 1, which can make the fallback confidence appear stronger than the underlying evidence supports.

6. Video indexing pipeline
Current indexing process
The active indexing script is index_youtube.py.

Its process is:

Require TWELVE_LABS_API_KEY.
List available Twelve Labs indexes.
Find the first index named SceneIt_MVP.
Create that index if it does not exist.
Parse an 11-character YouTube ID from the supplied URL.
Download the complete video using yt-dlp.
Store it temporarily as youtube_download.mp4.
Open the file and upload it to Twelve Labs.
Poll the Twelve Labs task every five seconds.
When indexing succeeds, get the Twelve Labs video ID.
Save the association between:
Twelve Labs video ID
YouTube video ID
Delete the temporary MP4.
Print the index ID so it can be added to configuration.
Example invocation:

python index_youtube.py "https://www.youtube.com/watch?v=VIDEO_ID"
Mapping format
The mapping file conceptually contains:

{
  "twelve-labs-video-id": "youtube-video-id"
}
This mapping is essential because Twelve Labs search returns its own internal video ID, while the YouTube player needs the original YouTube ID.

Important migration contradiction
The historical YouTube migration requirement explicitly requested:

Direct URL-based Twelve Labs indexing
No local video download
No yt-dlp
No temporary MP4 file
The current implementation does the opposite:

YouTube URL
    ↓
yt-dlp
    ↓
temporary MP4
    ↓
Twelve Labs file upload
Therefore, the YouTube migration is only partially complete.

The user-facing playback was migrated to YouTube, but the ingestion side remains based on local downloading.

Indexing risks
The current indexing approach has several weaknesses:

Uses one fixed temporary filename
Concurrent indexing commands can overwrite each other
No polling timeout
No backoff strategy
No interruption-safe cleanup
No retries for transient provider failures
No duplicate-video detection
No idempotency
No atomic mapping writes
No mapping schema validation
No administrative UI
Index selection is based on name, which is ambiguous if duplicate indexes exist
The index ID still has to be transferred manually into application configuration
Full video downloads consume disk, time, bandwidth, and potentially create platform or content-policy concerns
7. Frontend behavior
Search experience
The homepage contains:

SceneIt branding
“Moment Finder v1.0” label
A natural-language text input
A large “Find It” button
Enter-key submission
During search, it shows a simulated terminal-style animation with text such as:

“Scanning video index”
“Analyzing visual patterns”
“Cross-referencing semantic data”
“Locating timestamp”
This animation does not reflect individual backend stages; it is purely a loading presentation.

Search states
The frontend supports:

Initial search state
Loading state
Match state
No-match state
Error state
Reset/search-again state
Video player behavior
After a match:

The result start and end timestamps are saved in browser variables.
The displayed confidence is converted to a percentage.
A YouTube player is mounted.
The player seeks to the start time.
Playback begins.
A 250-millisecond interval monitors playback.
If the player reaches the end time, it seeks back to the start.
If the user pauses, the code attempts to play again.
This creates an approximate looping clip without creating a new video asset.

Limitations of the player implementation
Browser autoplay policies may prevent playback.
Player errors are not handled.
The YouTube API readiness poll has no timeout.
The loop depends on frequent browser polling rather than a more explicit player-state design.
Buffering can affect loop timing.
Returned timestamps are not validated.
The user is intentionally prevented from pausing normally.
Hidden controls and disabled fullscreen may hurt accessibility.
Reset logic can create duplicate yt-player element IDs after repeated searches.
There is no cancellation when a second search supersedes the first.
There is no loading timeout.
8. Sharing behavior
A share button is implemented using:

Web Share API when available
Clipboard API as fallback
The shared text includes the user’s query.

However, the shared URL is only the current homepage URL:

window.location.href
It does not contain:

The query
YouTube video ID
Start timestamp
End timestamp
A result identifier
Consequently, another person opening the shared link will only see the initial homepage. They will not see the actual found scene.

So the sharing button exists, but reproducible scene sharing is not complete.

There is also a bug in the clipboard error path: when copying fails, the app displays “Link copied!” anyway.

9. Legacy local-video approach
The original version used a local test_video.mp4.

setup_index.py:

Creates or finds the same Twelve Labs index
Uploads test_video.mp4
Copies the video to static/test_video.mp4
Polls for indexing completion
This reflects the first project architecture:

Local MP4 → Twelve Labs index → local HTML5 playback
The application later moved to:

YouTube source → Twelve Labs index → YouTube iframe playback
setup_index.py is documented as deprecated and is incompatible with the current YouTube mapping system because it never associates uploaded videos with YouTube IDs.

It should not be carried into a clean rebuild unless local uploads are intentionally part of the new product.

10. RunPod/Qwen experiment
What it does
ping_runpod.py is a standalone diagnostic for a hosted vision-language model.

It:

Reads RunPod credentials/configuration
Creates an OpenAI-compatible client
Uses a RunPod endpoint URL
Targets Qwen/Qwen2.5-VL-72B-Instruct-AWQ
Generates a tiny synthetic PNG in memory
Encodes it as a base64 data URL
Sends a multimodal Chat Completions request
Asks the model to describe the action in the image
Prints the model response
What it does not do
It is not connected to:

Flask
/search
Twelve Labs
YouTube indexing
Timestamp retrieval
The browser interface
video_mapping.json
The image it sends is currently only a 50×50 solid-color synthetic test image. That is suitable for verifying request-format compatibility, but not for evaluating scene understanding.

The repository also includes maxresdefault.jpg, apparently intended as a more meaningful test image, but the script does not use it.

Architectural significance
RunPod/Qwen cannot directly replace Twelve Labs without substantial new infrastructure.

Qwen currently takes an image and returns prose. SceneIt needs:

Video ingestion
Frame extraction
Audio/transcript handling
Temporal indexing
Embedding generation
Semantic retrieval
Timestamp aggregation
Result ranking
Confidence scoring
Persistent video metadata
If RunPod is intended to become the main engine, the new project would need a complete custom video-analysis pipeline rather than a simple API substitution.

The RunPod work should currently be considered an experiment, not an in-progress integrated feature.

16. Security and reliability considerations
Error leakage
The backend returns raw exception text to the browser:

{"error": str(e)}
Provider errors can expose internal operational details. Production code should log the full error server-side and return a safe public message.

No abuse protection
POST /search has no:

Authentication
Rate limiting
Request quotas
Maximum query length
Per-IP restrictions
Bot protection
Provider-cost protection
A public deployment could generate uncontrolled Twelve Labs usage.

Weak request validation
The code assumes the request body is JSON and that .get() is available. Malformed or missing JSON can cause an exception.

There is also no validation of returned timestamps, confidence values, or video IDs.

Local persistence
video_mapping.json is:

Read directly from disk
Rewritten in full
Not locked
Not atomically replaced
Not backed up by the application
Not suitable for autoscaling
External dependencies
The frontend requires:

Tailwind CDN
Google Fonts
YouTube IFrame API
Failures or blocking of those services can degrade the interface.

Search timeouts and retries
The application does not define explicit Twelve Labs request timeout or retry behavior. Indexing polling can continue indefinitely.

22. Final assessment
SceneIt has successfully proven its central product idea:

A user can describe a moment, search semantically indexed video content, receive a timestamp range, and watch the corresponding YouTube segment.

That is the most valuable accomplishment and should guide the rebuild.

The existing project is best viewed as a proof of concept demonstrating three important integrations:

Twelve Labs can locate semantically relevant video segments.
Provider video IDs can be mapped back to playable YouTube sources.
The browser can turn returned timestamps into a looping scene.
For the migration, preserve those validated ideas but rebuild the surrounding system around:

Durable metadata storage
A formal provider adapter
Safe and idempotent ingestion
Stable shareable scene URLs
Explicit configuration
Automated tests
Rate limiting and observability
A clear decision about whether RunPod is experimental or strategic
The most immediate next step should be to define the new architecture and API contracts, then rebuild the current Twelve Labs-based MVP before adding broader functionality or attempting a custom RunPod-powered replacement.
